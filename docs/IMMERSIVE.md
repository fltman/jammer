# Immersive audio (phase 4): sketch and what is built

Phase 4 of `docs/PLAN.md`: multichannel up to 7.1.4, ADM BWF, Ambisonics, APAC/ASAF export, binaural monitoring with head tracking, Overdub with consent flow. Sketched 2026-11-17 on the coordinator's word to build block D on my own judgment; numbers from standards are written in only after they have been read at the source (the sources are named where they are used).

## Order

1. **Channel-based documents beyond stereo** (D1): a document has a layout (mono, stereo, 5.1, 7.1, 7.1.4). Every source is mapped into it by a matrix made from the two layouts (a mono voice to the centre, a stereo pair to L and R, a wider source folded down by the standard's coefficients). Playback on a device with fewer channels is folded down at the output. The loudness meter weights the channels by their place. WAV/RF64 written with the channel mask; FLAC up to 8 channels; MP3 and Opus stay mono/stereo. A step changes the layout as a value of the project, so it is undone like any other.
2. **A surround panner** (D2): a track's position (azimuth, elevation, spread) in a layout wider than stereo, written with the published amplitude-panning method it uses; automatable like pan.
3. **ADM BWF** (D3): a bed (channel-based) written as BW64 with `chna` and `axml` by the common definitions, and read back.
4. **Ambisonics** (D4): AmbiX (ACN/SN3D) documents, a source encoded into them by direction, and decoded to a layout or to headphones.
5. **Binaural monitoring with head tracking** (D5): through the system's own renderer where it can take the document's channels; otherwise not built.
6. **APAC export** (D6): where AudioToolbox can write it.
7. **Overdub with consent flow**: built 2026-11-17 (ElevenLabs with the user's own key; `site/manual/23-overdub.md`, `docs/LICENSES.md`).

## Decisions (2026-11-17)

- **The layout is the document's; a source keeps its own.** Nothing is converted on import. A 5.1 file in a stereo document is heard folded down; set the document to 5.1 and it is heard as it is. No edit touches a source file.
- **Old documents render as they did.** A document without a layout is mono or stereo by its channel count, and mono and stereo sources go into it the old way (a mono source in both channels). The matrix is used only where a layout wider than stereo is involved, so the null tests stay as they are.
- **The order of the channels is the WAV order** (by the channel mask's bits). 5.1's surrounds are written as the side pair (mask 0x60F); a 5.1 file with the back pair (0x3F) is read as the same layout.
- **Pan is stereo's.** In a wider document a track's stereo pan is not offered until the surround panner (D2) is there; the step says so.
- **Monitoring is not the mix.** The fold-down at the output is for listening only; an export is always in the document's layout unless a step says otherwise.

## Built

### D1, first part (2026-11-17, not yet used by the documents)

- `ChannelLayout` and `Speaker` (`JammerCore/ChannelLayout.swift`): the five layouts, their loudspeakers in WAV order, the mask; a file's layout from its mask or count.
- The engine: a matrix per source in a plan (`jm_plan_set_source_matrix`); without one a plan renders as before. Tested: a mono voice into 5.1 lands in the centre only and a stereo pair in L and R, sample for sample; a fold-down sums by its gains.
- The output: a slot has a gain, and several slots can add into one device channel (`jm_engine_set_output`'s `gains`). Tested through the device callback: L, R and C on a stereo device give L + 0.707·C and R + 0.707·C within 10⁻⁶.

### D1, second part (2026-11-17)

- **A file in a known layout opens as a document in that layout** (a 5.1 WAV is a 5.1 document); a file in another layout is heard as stereo, as before. A document wider than stereo is saved as format 4, which an older Jämmer refuses rather than playing a mono voice in every channel; a project with a channel count that is no layout (4, say) is refused when read.
- **Sources go into the document by the matrix**: a mono source to the centre, a stereo pair to L and R, a source in the document's own layout channel for channel. Tested: a 5.1 file in its 5.1 document nulls; a voice and a stereo pair in a 5.1 document land in C and in L/R sample for sample, with nothing in the LFE or the surrounds; the same sources in a stereo document are as they were.
- **Pan** in a wider document is refused with words that say so ("this one is 5.1, and its surround panner isn't built yet"), in both languages, and so is pan automation.
- **The export** writes the layout's channel mask (5.1 as the side pair, 7.1.4 as 0x2D63F); the status bar names the layout.

### D1, third part (2026-11-17): fold-downs, the meter, listening, the layout menu

- **Fold-downs** (`ChannelLayout.gains`), a layout at a time:
  - 5.1 to stereo and to mono: ITU-R BS.775-4, Annex 4, Table 2: L′ = L + 0.7071 C + 0.7071 Ls (R′ likewise); mono C′ = 0.7071 L + 0.7071 R + C + 0.5 Ls + 0.5 Rs. The LFE has no column there and is left out.
  - 7.1 to 5.1: the sides and the rears into 5.1's surrounds at 0.707 each: AOMedia IAMF 2.0.0, Annex A2.2, Ls5 = α·Lss7 + β·Lrs7, mode 2 (α = β = 0.707).
  - 7.1.4 to 7.1: each height into the loudspeaker under it at 0.7071 (top fronts into L and R, top rears into the rears). **Jämmer's own choice:** no standard read gives a fold of the heights into the ear layer (BS.775 has no heights; IAMF's quoted steps fold heights into heights; AOM's renderer's static matrices stop at 3.1.2). It uses the same −3 dB as the others.
  - No normalisation, as in BS.775: a fold-down can be louder than its parts and can clip; the meters show it.
  - Tested: each coefficient; 7.1.4 into stereo through every step (a top rear reaches the left at 0.7071³); a 5.1 file in a stereo document is heard as L + 0.7071 C + 0.7071 Ls within 10⁻⁶.
- **Listening:** a document wider than the device is folded down to the device's stereo pair by the same coefficients; a device with enough channels gets one each. Tested on the routing (5.1 onto a stereo pair, onto a four-channel device's chosen pair, 7.1.4 onto two channels).
- **The loudness meter weights by position** (ITU-R BS.1770-5, Annex 3, Tables 4 and 5): 1.41 for 5.1's surrounds (±110°) and 7.1's sides (±90°), 1.00 for the fronts, 7.1's rears (±135°) and every height, the LFE not measured. Until today 7.1's rears had 1.41 and 7.1.4's LFE was counted. Tested: EBU Tech 3341 case 6 (a 5.0 sine, −28/−24/−30 dBFS) made here from its definition reads −23.0 ±0.1; a tone in each loudspeaker of 5.1, 7.1 and 7.1.4 reads as its weight says (sides +1.49 dB, LFE nothing); a 5.1 programme agrees with ffmpeg's ebur128 within 0.15 LU.
  - **Calibrated for 7.1 and 7.1.4 against ITU-R BS.2217-2** (block J, below): the ITU's 0+7+0 and 4+7+0 compliance files read −23.000, −24.000 and −23.001 LKFS. ffmpeg's ebur128 gives 7.1's rears 1.41 (its source, read 2026-11-17), so it is no reference there.
  - EBU's own test files can't be committed either ("You may not use any EBU Test Sequences for business, commercial or for-profit activities"); the cases are tones defined in Tech 3341's table, so they are made in the tests.
- **Audio › Layout** (Mono, Stereo, 5.1, 7.1, 7.1.4, the document's ticked) and the step `set_layout`: a value of the document, undone like any other; nothing converted. `layout` in `GET …/documents/{id}`.

- **Seen in the app** (2026-11-17, a 5.1 WAV with a tone in each channel): it opens as 5.1 and the status bar says "5.1"; Audio › Layout lists Mono, Stereo, 5.1, 7.1, 7.1.4 with 5.1 ticked; choosing Stereo and ⌘Z brings it back; two seconds of playback on the Mac's stereo output, folded down, with no underrun; the mixer's description wraps to a narrow window.

### D2, first part (2026-11-17): the surround panner

- **A track's place** (`SurroundPosition`: azimuth, elevation, width) in a layout wider than stereo, by the angles of ITU-R BS.2051-3 (azimuth positive to the left; read at the source: "positive values rotate to the left"). The loudspeakers' nominal directions from its tables: fronts ±30°, 5.1's surrounds ±110°, 7.1's sides ±90° and rears ±135°, 7.1.4's heights at ±45° and ±135°, 30° up.
- **The panner** (`Panner`): vector base amplitude panning (V. Pulkki, J. Audio Eng. Soc. 45(6), 1997) between the two loudspeakers of a layer that enclose the direction, scaled to constant power; where there are heights, the ear layer and the height layer crossfaded by elevation at constant power from 0° to 30°; above 30° the sound stays in the height layer (there is no loudspeaker overhead). The LFE is never fed. A mono source is placed at the azimuth; a stereo source's two sides at azimuth ± width/2. On a loudspeaker's own direction only that loudspeaker sounds, so the default place (0°, 60° wide) gives exactly the old routing: a voice in C, a pair in L and R. A source of more than two channels on a placed track stays on its own loudspeakers.
- **Steps:** `set_track` takes `azimuth`, `elevation`, `width`, and `placed: false` to take a track out of the panner; refused in mono and stereo ("Use pan"), and pan is refused in a wider document ("Place a track with azimuth instead"), in both languages. `position` on each track in `GET …/mixer`.
- **The mixer:** a track's strip in a wider document has an azimuth slider (left to the left, either end behind) and a menu with its place in words ("Left 110°", "Own loudspeakers"), the height in 7.1.4 (0°, 15°, 30°), and Back on Own Loudspeakers.
- **Tested:** the gains on each loudspeaker's direction, halfway between two, behind; constant power and no LFE at every 7.5° in 5.1, 7.1 and 7.1.4; heights at 30° and above, and halfway at 15°; the default place equals the old routing; a voice placed at 110° plays in Ls sample for sample and nowhere else; saved and read back; out of range refused. **Seen:** the mixer with a voice placed at 110° ("Left 110°", the slider to the left), the layout menu's words.

### D5, first part (2026-11-17): binaural listening, without head tracking

- **Audio › Listen on Headphones (Binaural)** (a setting of the app, ticked when on; for documents wider than stereo): the engine feeds Apple's spatial mixer (`AUSpatialMixer`) with the document's channels as a bed (`kSpatialMixerSourceMode_AmbienceBed`, each channel from its loudspeaker's direction by the bus's channel layout: 5.1 as `MPEG_5_1_A`, 7.1 as `WAVE_7_1`, 7.1.4 as `CICP_19`, the tags whose order is the WAV order), rendered for headphones (`kSpatializationAlgorithm_UseOutputType`, `kSpatialMixerOutputType_Headphones`), and the mixer feeds the default output. Nothing of it runs in Jämmer's code on the audio thread: the engine's render callback is the same one the output unit uses. Listening only: exports and meters are the document's channels.
- **Tested** offline (the mixer rendered from a test, no device): a tone in 5.1's left surround is more than 3 dB louder at the left ear, the right surround at the right, the centre within 1 dB at both, 7.1.4's left top front at the left ear. **In the app:** playback through it with no underrun, the menu's tick, back to loudspeakers. **Not heard:** the test copy's output is silent; how it sounds is for Anders with headphones.
- **Head tracking (block K, below)** is built the other way: the app reads the headphones' motion itself (Core Motion, no entitlement) and turns the spatial mixer's listener. The mixer's own head tracking needs `com.apple.developer.coremotion.head-pose`, which only a provisioning profile can give.

### A fault found and mended on the way (2026-11-17)

The document's audio output and its plugin host were made once, for the channel count the document had when it was opened. After Audio › Layout changed the count, the engine would have been handed a plan of another width than its ring. Now both are made again when the count changes (playback stops, plugins start again). Seen: the layout changed while playing, then stereo and 5.1 played again without underruns.

### D6, first part (2026-11-17): APAC export

- **APAC in MP4** for documents in 5.1, 7.1 and 7.1.4 (`APACWriter`; File › Export's format list offers "APAC (MP4)" for those documents, and no MP3 or Opus; the API's `format: "apac"`). Written through AudioToolbox with the encoder of macOS 26 and later, the channels as a bed in the layout tag whose order is the document's; the settings Apple's APAC paper (June 2025) asks for: content source 38 ("Traditional professional AV offline encoded content such as stereo and multichannel"), the loudness/DRC configuration Movie (the paper: "None should not be utilized"), a sync packet every 75 packets. The encoder chooses the bit rate.
  - AVAssetWriter was tried first and refuses every content source but Apple's own (1–10: "content source must be between AVAudioContentSource_AppleCapture_Traditional and AVAudioContentSource_ApplePassthrough"), which would label this as Apple's content; AudioToolbox takes the third-party values, as the paper's own `afconvert -u csrc 36` example does.
  - A loudness delivery target is not measured through APAC (it carries its own loudness metadata, which a decoder applies).
- **Tested:** a 5.1 and a 7.1.4 document written, decoded again by Apple's decoder: the channel count, the format, and every channel's tone loudest in its own channel. **In the app:** a 5.1 document exported through the API; `afinfo` reads "6 ch, 48000 Hz, apac … Channel layout: 5.1 (L R C LFE Ls Rs)"; a stereo document is refused in words. **Seen:** the export panel's Format menu, read while open: for a 5.1 document WAV, AIFF, FLAC, ALAC, AAC and APAC (MP4), no MP3 or Opus; for a stereo document MP3 and Opus and no APAC.
- **Not built:** Ambisonics and objects in APAC (no Ambisonics documents yet; Jämmer has no objects); ASAF (Apple publishes no authoring interface for it).

### The waveform where the sound is heard (2026-11-17)

In a layout wider than stereo the timeline draws a clip through the same matrix as its sound: a voice in the C row only, a placed voice at its loudspeakers, a wider source folded down into the document's rows (as the envelope of the summed parts). Seen before the change: a voice placed at Ls was drawn in L and R. Tested on the columns, and seen after it: a voice placed at 110° is drawn in the Ls row, a little in Rs.

### D4, first part (2026-11-17): Ambisonics documents

- **AmbiX** (C. Nachbar, F. Zotter, E. Deleflie, A. Sontacchi, "ambiX – A Suggested Ambisonics Format", Ambisonics Symposium 2011, read at the source: ACN order, SN3D, no Condon-Shortley phase), first to third order (4, 9, 16 channels), as layouts in Audio › Layout and `set_layout` (`ambix1`, `ambix2`, `ambix3`).
- **A file is never taken for a sound field:** nothing in a WAV says its 4, 9 or 16 channels are Ambisonics, so it opens as stereo as before, and the document is set to the order by hand; the file then passes through channel for channel (tested, sample for sample).
- **Encoding** (`Ambisonics.encode`): the real spherical harmonics up to third order. Tested on SN3D's defining property: W is 1 and each order's squares sum to 1 in every direction (every 15°), and on the first order's directions. Into a sound field a mono source comes from the front, a placed track from its place (the panner's azimuth and elevation, every elevation), a loudspeaker layout from its loudspeakers' directions (the LFE left out); one order goes into another by the components they share.
- **No decoder (until block I, below):** a sound field in a loudspeaker document was meant to be left out; in fact no file was ever taken for a field, so a 16-channel file in a 7.1.4 document went channel for channel into the first 12 loudspeakers. Listening to an Ambisonics document always goes through Apple's spatial mixer with Core Audio's `HOA_ACN_SN3D` tag: for headphones when binaural listening is on, otherwise for loudspeakers. Tested offline: a tone encoded at 90° left reaches the left ear more, at 90° right the right ear, at first and third order. In the app: played both ways without underruns (`outputPath` `spatialSpeakers` and `binaural`); not heard.
- **Loudness isn't measured** in an Ambisonics document: ITU-R BS.1770 has no weighting for a sound field, and no reference has been found. `GET …/analysis`, the dialogue analysis, `normalize` to a loudness, `loudness_preset`, `limit` and an export's `targetLUFS` are refused with that reason (`not_available`). The meter internally takes only W, so nothing breaks, and nothing of it is shown.
- **APAC** writes a sound field too, with the HOA tag and content source 39 ("Spatial professional AV offline encoded content"): `afinfo` reads "4 ch, 48000 Hz, apac … Channel layout: High-Order Ambisonics, ACN/SN3D". A WAV export of a field is written with a channel mask of 0 (no loudspeaker positions).

### Block I (2026-11-17): a field decoded to loudspeakers, and turned

**Which files are fields.** A source is a sound field when its document was made Ambisonics of its order (`set_layout ambixN` marks every file of (N+1)² channels with no loudspeakers named in it), or by `set_track` `field` (1–3, 0 to unmark; a file of another size is refused). The mark stays when the layout changes, so a field made in an Ambisonics document is decoded when the document becomes 5.1, 7.1 or 7.1.4. Saved as project format 5: an older Jämmer refuses the file instead of playing a field's components straight into loudspeakers. A mark that doesn't fit its file's channels (a hand-edited project) is dropped when the project is opened.

**The decoder: AllRAD** (F. Zotter, M. Frank, "All-Round Ambisonic Panning and Decoding", JAES 60(10), 2012; read as described in E. M. Hoffbauer's master's thesis at KUG/IEM, 2021, §1.2.3, the paper itself being behind the AES e-library and Zotter and Frank's open-access book not reachable from here). Two stages: the field is sampled on a dense set of virtual loudspeakers with max-rE weights (a_n = P_n(cos(137.9°/(N+1.51)))), and each virtual loudspeaker is panned onto the real ones by VBAP over the convex hull of the real loudspeakers and imaginary ones that close it: below always, and above a layout without heights (5.1, 7.1); the imaginary loudspeakers' signals are dropped, as the thesis describes. The LFE gets nothing.
- **A deviation, said:** the virtual loudspeakers are an exact quadrature grid (24 Gauss–Legendre nodes in the sine of the elevation × 48 azimuths, with their weights) instead of a t-design: it integrates the same products exactly, and needs no table of points from anyone. The level: a source's energy over the loudspeakers averages 1 over the sphere.
- **Into mono or stereo** a field is decoded into 5.1 and folded down by ITU-R BS.775, as any 5.1 source is.
- **Checked against the method's own measures** (Gerzon's energy E and energy vector rE, `AmbisonicDecoder.measure`), every 5° of azimuth:

| Layout, order | Ear plane: E | rE direction error (max / mean) | \|rE\| | Upper half (15–60° up) |
|---|---|---|---|---|
| 5.1, 1 / 2 / 3 | −2.4…2.4 / −1.5…2.8 / −1.1…2.7 dB | 19 / 9°, 26 / 7°, 23 / 8° | 0.34…0.77 / 0.90 / 0.94 | no heights: errors up to 63°, as expected |
| 7.1, 1 / 2 / 3 | −0.4…1.8 / 0.0…2.9 / 0.2…3.0 dB | 6 / 3°, 5 / 2°, 11 / 2° | 0.64…0.73 / 0.89 / 0.94 | no heights: up to 61° |
| 7.1.4, 1 / 2 / 3 | −0.6…0.6 / −0.9…1.0 / −0.9…1.1 dB | 22 / 18°, 12 / 10°, 12 / 7° | 0.61…0.69 / 0.86 / 0.91 | E 0.0…1.7 dB; 15 / 5°, 11 / 6°, 19 / 8° |

- **Its limits, as measured:** in 5.1 the gap behind (between ±110°) is where the direction errs most (up to 26°); in 7.1.4 a source at ear level is pulled upward by the heights (7–18° on average, most at first order): the imaginary loudspeaker below takes the lower half's share and is dropped. Nothing above or below a layout without heights can be placed there; it lands on the ear-level ring.
- **Not compared** with another decoder (none was fetched); not heard on loudspeakers.

**The turn** (yaw, pitch, roll, degrees; roll about the front axis lifting the left side, then pitch lifting the front, then yaw to the left as an azimuth): each order's band rotated into itself, worked out as R_n = (2n+1) Σ w Y_n(turned point) Y_n(point)ᵀ on a 4 × 8 Gauss product grid, exact for SN3D up to third order. Checked against its definition: a turned field is the field of the turned direction, within 10⁻⁵, at every order, in every direction tried.
- **Fixed** (`set_track` `yaw`, `pitch`, `roll`; `turned: false` takes it away; the mixer's slider and menu for a track that plays a field): baked into the field's matrix.
- **By lanes** (`set_automation` `param` `yaw`, `pitch`, `roll`, debug builds with the rest of automation; View › Automation › Field Turn, Field Front, Field Side): the engine works the matrix out on the 512-frame grid and, between grid points, follows a curve through the next two (a straight ramp would miss by its chord, which grows with the order: about 6·10⁻⁵ at third order for 40°/s). Where a lane turns within two steps the curve would overshoot, so there the matrix is also worked out at the lane's own point and goes straight to it and on. Only grid points and lane points: a render from the middle gives the same samples (tested).
- **Tolerance against the ideal path** (every sample turned at its own angle), as for the place lanes: along a straight stretch 2·10⁻⁵ (measured: 5·10⁻⁷ for 80° in 2 s, third order); at a point where the lane reverses at 58°/s, within 10⁻⁴ (measured: 9.5·10⁻⁵), well inside the place lanes' 2·10⁻³.
- **Nothing on the audio thread allocates:** the quadrature's directions, weights and harmonics are made when the plan is built; `-Werror=function-effects` holds the turn's matrix and the curve's lookup (marked `JM_NONBLOCKING` here) to that, and refused the curve's lookup until it was marked.
- **A bus's field (2026-11-28):** in an Ambisonics document a bus is turned the same way (`Bus.rotation`; `set_bus` `yaw`, `pitch`, `roll`, `turned: false`; lanes `yaw`, `pitch`, `roll` on the bus; the mixer's slider and menu on its strip), after its fader: the engine's `FieldTurn` with the identity as its base (`jm_plan_set_bus_field_turn`), on the same grid and curve as a track's, so a field turned on its bus is the same field turned on its track (tested within 10⁻⁵ of the peak, lanes with a corner off the grid included; fixed, within 2·10⁻⁵ of the turned direction; a render from the middle gives the same samples). In a loudspeaker layout a bus is turned by azimuth instead, and a field's turn is refused there in words. A frozen bus is frozen before its turn, which comes after the file as its fader does. (Head tracking is block K: it turns the listening, not the field.)

### Block J (2026-11-17, by Anders's leave): loudness calibrated against BS.2217, and ADM BWF

**BS.2217.** Report ITU-R BS.2217-2 (10/2016), "Compliance material for Recommendation ITU-R BS.1770", read at the ITU: each file shall read its value within ±0.1 LKFS. Its files fetched from itu.int (the report's link, R1102000001) into a folder outside the repository ("All rights reserved"; not committed); `BS2217Tests` runs when `JAMMER_BS2217=<folder>` is set.

| File (BS.2217-2) | The report | Jämmer |
|---|---|---|
| Mono Voice+Music −23 / −24 | −23.0 / −24.0 | −22.991 / −23.994 |
| Stereo VinL+R −23 / −24 | −23.0 / −24.0 | −22.979 / −23.976 |
| 6ch VinCntr −24; VinL+R −23 / −24; VinL-R-C −23 / −24 | as named | −23.977; −22.989 / −23.988; −22.986 / −23.976 |
| 8 channels (0+7+0) −23 / −24 | −23.0 / −24.0 | −23.000 / −24.000 |
| 12 channels (4+7+0) −23 | −23.0 | −23.001 |

- **The files have no channel mask**, and their order is the report's, BS.2051's: L R C LFE **Lss Rss Lrs Rrs** (then Tfl Tfr Tbl Tbr), the sides before the rears. Jämmer reads a WAV without a mask in the mask's order (L R C LFE **Lrs Rrs Lss Rss**, as ffmpeg does), so the test moves the channels as a mask would. Read in the mask's order the 8-channel files give −22.919 / −23.927 (inside ±0.1 by 0.01) and the 12-channel one −23.106 (outside): the rears would get the sides' 1.41. Which order a file without a mask means is not settled by any standard read (WAV's own convention has none past stereo). **Anders chose BS.2051's** (2026-11-17), and the coordinator asked for the choice to be the user's too:
  - A user's own 7.1 or 7.1.4 WAV/AIFF without a mask or ADM opens in BS.2051's order (`SourceRef.opened()`), and the status line says so and where to change it. Files Jämmer writes itself (frozen tracks, repairs, a decoded MP3 or FLAC) are in its own order, the WAV mask's, and are not touched; nor is a project saved before (no order on its sources: the WAV order, as it was heard).
  - **Audio › Layout › Unmarked File: Sides First (ITU-R BS.2051) / Rears First (WAV Order)**, shown only when the document has such a file; `set_layout` `order` (`bs2051`, `wav`; anything else refused by name; refused where no file leaves the order open) and `?order=` when the API makes a document. A value of the document, undone like any other; nothing converted. Saved as project format 6 when a file is heard in BS.2051's order, so an older Jämmer refuses it rather than hear it the other way round.
  - A file with a mask or ADM's `chna` is always heard by it. Film order (L C R …) is not offered: no source for it was read.
  - The BS.2217 test opens the ITU's files as the app does and measures what the document plays: −23.000 / −24.000 / −23.001 in BS.2051's order, −22.919 / −23.927 / −23.106 in the WAV order.
- The 10-channel (4+5+0) and 24-channel (9+10+3) files are layouts Jämmer has no document for; not measured.

**ADM BWF (D3).** A WAV export of a 5.1, 7.1 or 7.1.4 document is now an ADM BWF file: besides its mask, a `chna` chunk names each track by the common definitions' track format and the layout's pack format, and an `axml` chunk (EBU Core 2016 namespace) holds one programme, one content and one object with every track (ITU-R BS.2088's chunks, BS.2076's elements). The packs are the common definitions' (ITU-R BS.2094): 5.1 `AP_00010003`, 7.1 with its rears at ±135° `AP_0001000f` ("7.1back", 0+7+0), 7.1.4 `AP_00010017` (4+7+0); 5.1's surrounds are the ±110° channels, 7.1's sides ±90°, the heights ±45° and ±135° at 30° up, as Jämmer places them. Read in the common definitions as the EBU's renderer ships them (`2094_common_definitions.xml`); nothing of its code used. Written as RIFF under 4 GB and RF64 above, as before (the renderer reads both).
- **Read back:** a file's `chna`, when it names every channel once by a loudspeaker of 5.1, 7.1 or 7.1.4, decides the order over the mask and the channel count, so a file in BS.2051's order without a mask plays each channel from its own loudspeaker. A `chna` that doesn't (a track twice, a channel missing, another loudspeaker, an object) is ignored and the file read as before. The chunks of a source are kept in its file, as all foreign chunks are; an export writes its own.
- **Checked with the EBU's ADM renderer** (`ear` 2.1.0, BSD-3-Clause-Clear, installed by Anders's leave in a venv outside the repository with an existing Python 3.11 and `setuptools<70` for its `pkg_resources`; `JAMMER_EAR=<path to ear-render>`): with `--strict` it reads each of Jämmer's three beds and renders it to its own layout (0+5+0, 0+7+0, 4+7+0) channel for channel, difference 0.0 on 24-bit files. **Through the app:** a 7.1.4 document named `Bed & "Atmos"` exported as WAV by the agent API, rendered by `ear-render --strict -s 4+7+0`, gives back the source's channels exactly (0.0), the name escaped in `axml`.
- **Objects (2026-11-28):** a WAV export of a 5.1, 7.1 or 7.1.4 document can write each placed track as an ADM object (`ADMObjects`, read in ITU-R BS.2076-3 at the source: § 5.3–5.6, 5.13, 6, 7, 8 and Annex 2 § 3). The file's first channels are the bed, rendered from the document with those tracks' own sound routed to a muted bus, so their sends to buses (a reverb) are still in it; each object follows in a channel of its own, its track alone after its plugins and fader, before the panner (a stereo track two objects, its left and right at azimuth ± width/2, where the panner puts them). Each object is typeDefinition Objects (0003) with custom pack, channel, track and stream formats from 1001 and PCM track and stream formats as Annex 2's example has them; its place is polar (azimuth −180…180 positive to the left, as Jämmer's, elevation, distance 1), one block when it doesn't move, else a block per stretch between automation points at its end's place (jumpPosition 0) or held from its start (1) where the lane holds; times in the exact sample form (`hh:mm:ss.zzzzzSfffff`). The master's level is in every channel; its limiter only in the bed's (the objects don't pass through it). Agent: `POST …/export` with `objects: true`.
  - **Read back** by Jämmer: `AudioFileReader.admObjects` reads a file's objects with their tracks (from `chna`) and blocks; ADMObjectsTests write a 5.1 document with a moving placed voice as the export does and read back seven channels, the object's blocks as written and the voice alone in its own channel. The XML is checked against BS.2076-3's structure by XPath.
  - **Not tried with another program.** The EBU's renderer isn't installed on this Mac now (the one used for the beds was in a venv that is gone), and installing it waits for Anders's yes; no DAW has read one either. So it is not known that another tool renders Jämmer's objects where Jämmer places them. On Anders's list.
  - **Not built:** Ambisonics as ADM (HOA type); opening an ADM file's objects as placed tracks (they are read, but a file opens as its channels); objects at another sample rate than the document's, from some tracks only, or in another format than WAV; an object's width, diffuse or divergence. A mono or stereo WAV gets no ADM.

### Block K (2026-11-17, by Anders's leave): the head followed while listening on headphones

- **How:** Core Motion's `CMHeadphoneMotionManager` gives the headphones' attitude (AirPods Pro, Max, 3rd generation and later); `HeadTracker` (the app) takes it relative to where the head pointed when following began or was centered, and `Output.head` sets the spatial mixer's `kSpatialMixerParam_HeadYaw`, `HeadPitch` and `HeadRoll` (global, degrees: −180…180, −90…90, −180…180, from the SDK's header). The mixer's own head tracking (`kAudioUnitProperty_SpatialMixerEnableHeadTracking`) needs the `com.apple.developer.coremotion.head-pose` entitlement, which only a provisioning profile can give; reading the motion ourselves needs only `NSMotionUsageDescription` (macOS asks the first time; the question is in English and Swedish, `App/InfoPlist.xcstrings`).
- **The mixer's convention, measured** (`BinauralTests.head`; the header says only degrees): HeadYaw positive turns the head to the **right** (a voice in front then reaches the left ear 5.9 dB more at +40°), HeadPitch positive looks up, HeadRoll positive tilts toward the right shoulder: the aircraft's. Jämmer's `HeadPose` turns left positive, as an azimuth, so the yaw changes sign on the way in. Pitch and roll were read from a source above and to the left (7.1.4's top front left): looking up it stays more to the side (7.7 dB) than looking down (5.4 dB); tilted to the right shoulder it stays to the left (6.5 dB), tilted to the left it comes over the head to the middle (−1.5 dB).
- **Core Motion's angles** are taken as its documentation's axes give them (yaw to the left, pitch up, roll): **not yet felt with real headphones.** If a turn goes the wrong way with AirPods, the sign is the one line in `HeadTracker` to change; Anders's listening kit checks each axis.
- **In the app:** Audio › Follow Head Movements (only while listening binaurally; off at every start, not remembered, so macOS's question only comes when asked for) and Audio › Center Head; the status line says what happened, and a denied permission or lost headphones say so and stop. The agent API reads it (`listening` in `GET …/documents/{id}`: binaural, headFollowed, head) and can't start it.
- **Tried** in a debug build with `-headTracking.simulate YES` (a slow turn of ±30° instead of the headphones): the menu refuses while binaural is off; on, the listener turns (yaw 26.3°, then −1.9° a moment later); off and binaural off both stop it; in English and Swedish. Nothing reaches the document, an export or a meter: the head is a property of the output only.
